## 2. 기능 A: 브라우저 북마크 가져오기

### 2.1 입력 형식

브라우저들은 `<!DOCTYPE NETSCAPE-Bookmark-file-1>` 형식의 HTML로 내보낸다. 이 앱의 `exportHTML`도 같은 형식(D-009).

```html
<DL><p>
  <DT><H3 PERSONAL_TOOLBAR_FOLDER="true">북마크바</H3>
  <DL><p>
    <DT><A HREF="https://github.com/" ADD_DATE="1700000100" ICON="data:...">GitHub</A>
    <DT><H3>개발</H3>
    <DL><p>
      <DT><A HREF="https://developer.mozilla.org/ko/" ADD_DATE="1700000300">MDN</A>
    </DL><p>
  </DL><p>
</DL><p>
```

- 폴더 = `<DT>` 안의 `<H3>` + 바로 뒤의 `<DL>`. 북마크 = `<A HREF>`. `ADD_DATE`는 **초** 단위(크롬·엣지·파이어폭스 HTML 모두).
- 최상위 폴더는 브라우저가 만든 것: 크롬·엣지 "북마크바/Bookmarks bar"(`PERSONAL_TOOLBAR_FOLDER`), "기타 북마크/Other bookmarks", "모바일 북마크", 파이어폭스 "북마크 도구 모음/Bookmarks Toolbar", "북마크 메뉴/Bookmarks Menu", "기타 북마크"(`UNFILED_BOOKMARKS_FOLDER`). 이 앱의 내보내기는 카테고리 없는 항목을 "기본 북마크" 폴더에 넣는다.

### 2.2 읽는 방법 (확인함)

브라우저 내장 **`DOMParser`**(`parseFromString(text, 'text/html')`)로 읽는다. 외부 라이브러리 없음.

- 모든 `a[href]`를 돌며, 조상 `<DL>`마다 그 부모 `<DT>`의 자식 `<H3>`를 모으면 폴더 경로가 된다. **2026-09-29에 크롬 형식 예제로 확인:** 3단계 중첩 폴더의 경로(`북마크바 / 개발 / JS`), `PERSONAL_TOOLBAR_FOLDER` 표시, 제목의 `&amp;` 같은 엔티티가 모두 올바르게 나옴.

```js
function folderPath(a) {
  const path = [];
  for (let dl = a.closest('dl'); dl; dl = dl.parentElement && dl.parentElement.closest('dl')) {
    const dt = dl.parentElement && dl.parentElement.tagName === 'DT' ? dl.parentElement : null;
    const h3 = dt ? dt.querySelector(':scope > h3') : null;
    if (h3) path.unshift(h3);
  }
  return path;
}
```

- **보안:** `DOMParser`로 만든 문서는 화면에 붙지 않아 스크립트가 실행되지 않고 이미지(`ICON` 등)도 받지 않는다. 가져온 값은 `textContent`·`getAttribute`로만 꺼내고, 그 뒤 **`normalizeBookmark`로 검증**한다(D-014). 파싱한 HTML을 화면에 넣지 않는다.
- 파일 형식 판별: 내용에 `NETSCAPE-Bookmark-file-1`이 있거나(대소문자 무시), 확장자가 `.html`/`.htm`이면 북마크 HTML로 본다. 아니면 지금처럼 JSON 백업으로 처리.
- 너무 큰 파일(예: 20MB 초과)은 읽기 전에 거절한다(폰 메모리 보호). 수천 개 규모는 문제없다.

### 2.3 변환 규칙

| 항목 | 규칙 |
|---|---|
| 카테고리 | 폴더 경로에서 **브라우저가 만든 최상위 폴더와 "기본 북마크"를 뺀 뒤 가장 안쪽 폴더 이름** (Q2). 남는 폴더가 없으면 `''`. 100자로 자름 |
| 제목 | `<A>`의 텍스트(앞뒤 공백 제거). 비었으면 **주소의 호스트 이름**(Q3). 500자로 자름 |
| URL | `HREF`. `http(s)`가 아니거나(`javascript:`, `chrome://`, `place:`, `file:` 등) 2048자를 넘으면 **건너뜀**. 스킴 보정(`https://` 붙이기)은 하지 않음 |
| 추가 시각 | `ADD_DATE`(초) × 1000. 값이 이미 ms(10¹²대)나 µs(10¹⁵대)로 보이면 자릿수로 맞춤. `isPlausibleTime`이 아니거나 없으면 `null` |
| 아이콘·`LAST_MODIFIED`·태그 | 버림 (앱에 없는 정보) |

- 브라우저 최상위 폴더 판별: `PERSONAL_TOOLBAR_FOLDER`·`UNFILED_BOOKMARKS_FOLDER` 속성이 있거나, 경로의 **첫 폴더**가 이름 목록(`북마크바`, `북마크 바`, `기타 북마크`, `모바일 북마크`, `북마크 도구 모음`, `북마크 메뉴`, `Bookmarks bar`, `Bookmarks Bar`, `Other bookmarks`, `Other Bookmarks`, `Mobile bookmarks`, `Bookmarks Toolbar`, `Bookmarks Menu`)에 있을 때. "기본 북마크"는 이 앱이 내보낸 파일에서만 나오므로 어느 위치든 `''`로 바꾼다 → **이 앱의 HTML 내보내기를 다시 가져오면 카테고리가 그대로 돌아온다.**

### 2.4 중복 건너뛰기와 추가 순서

- 같은 URL의 기준: **`new URL(url).href`가 같으면 같은 주소** (Q4). 호스트 대소문자, 기본 포트, 호스트만 있는 주소의 끝 `/`(`https://a.com` = `https://a.com/`)는 같게 본다. 경로 끝의 `/`, `http`↔`https`, 쿼리·해시가 다르면 다른 주소.
- 지금 목록에 있는 주소와, **파일 안에서 앞에 나온 주소**를 모두 건너뛴다.
- 가져온 항목은 파일의 순서대로 **목록 맨 앞**에 붙는다(D-004, JSON 병합과 같음). ID는 `sanitizeBookmarks(items, bookmarks)`가 새로 발급한다.
- 저장은 작업 함수 `mergeAll`로 한다 → 로컬 모드는 `localStorage`, 클라우드 모드는 500개 단위 배치 쓰기(D-020). 새 작업 함수·store 메서드는 필요 없다.

### 2.5 화면 흐름

1. 가져오기 버튼(Q1) → 파일 선택 → 파일 판별.
2. 북마크 HTML이면 변환·중복 검사 후 확인: "북마크 **N**개를 가져올까요?\n(이미 있는 주소 **M**개, 가져올 수 없는 항목 **K**개는 건너뜁니다.)"
   - 가져올 것이 0개면 이유만 알리고 끝.
3. 확인 → `mergeAll` → "북마크 N개를 가져왔습니다." 카테고리 필터 목록은 `renderBookmarks`가 자동으로 갱신.
- 계정 목록을 불러오는 중(K-16)에는 지금처럼 버튼이 막혀 있다.

### 2.6 테스트

- 크롬·엣지·파이어폭스에서 실제로 내보낸 파일, 이 앱의 `exportHTML` 파일(카테고리가 그대로 돌아오는지)
- 중첩 폴더, 최상위 폴더에 바로 있는 북마크, 빈 제목, `javascript:`·`chrome://` 주소, `ADD_DATE` 없음, 같은 파일을 두 번 가져오기(두 번째는 전부 건너뜀)

## 3. 기능 B: 바뀐 것만 받기

### 3.1 문제

지금은 로그인 중 `onSnapshot(orderBy('order'))`로 **컬렉션 전체**를 구독한다. Firestore는 리스너가 30분 넘게 끊겼다가 다시 붙으면 새 쿼리처럼 **결과 전체를 읽기로 계산**하므로, 앱을 열 때마다 대략 북마크 수만큼 읽힌다(K-18). 쓰기는 지금도 변경 1건당 1번이라 문제가 아니다.

### 3.2 방식 개요

1. **계정 목록의 사본을 `localStorage`에 둔다** (`single_file_bookmarks_cloud_copy_<uid>`). 앱을 열면 이 사본을 바로 보여 준다.
2. 사본에는 **마지막으로 받은 서버 시각 `lastSync`**를 함께 적는다. 리스너는 컬렉션 전체 대신 **`where('updatedAt', '>=', lastSync)`**만 구독한다 → 그사이 바뀐 문서만 읽힌다(결과가 0건이어도 쿼리당 최소 1회).
3. 삭제는 문서를 없애지 않고 **묘비** `{ deleted: true, updatedAt }`로 바꾼다. 문서를 지우면 "바뀐 것"으로 조회되지 않아 다른 기기가 알 수 없기 때문.
4. 받은 문서를 사본에 합치고(묘비면 사본에서 뺌) `lastSync`를 올린다. 사본이 없으면(새 기기, 로그아웃 뒤) **전체를 한 번 받는다.** 전체 받기는 `orderBy('order')` 조회로 한다 → `order` 필드가 없는 **묘비는 결과에 들어오지 않아** 묘비가 쌓여도 읽기가 늘지 않는다. 그 뒤 `lastSync`부터 바뀐 것만 구독한다.
5. 쓰기는 지금처럼 즉시 Firestore로 보낸다(오프라인이면 SDK가 대기열에 둠). 사본도 즉시 고친다.

Firestore의 IndexedDB 캐시(`persistentLocalCache`)는 그대로 쓴다. **앱을 닫아도 오프라인 쓰기 대기열이 남으려면 필요하다.** 사본은 "무엇을 보여 줄지", SDK 캐시는 "무엇을 올릴지"를 맡는다.

### 3.3 확인한 Firestore 동작 (2026-09-29, 실제 프로젝트에서 실험)

| 동작 | 결과 | 설계에 주는 영향 |
|---|---|---|
| `updatedAt >= T` 결과에 든 문서를 **이 기기에서 고치면** | 서버가 확정할 때까지 로컬 결과에서 빠짐(`removed`) → 확정되면 다시 `added`. `serverTimestamp()`가 확정 전에는 Timestamp가 아니라서 필터에 안 맞기 때문 | **`removed` 변경은 삭제로 보지 않는다.** 삭제는 묘비(`deleted: true`)로만 판단 |
| 같은 상황에서 서버가 쓰기를 **거부하면** | `removed` → 원래 문서가 다시 `added` | 위와 같음. 거부 처리는 3.5 |
| 지금 규칙에서 묘비 쓰기 | `permission-denied` | **규칙을 먼저 게시**해야 한다 (3.7) |
| SDK에 `where`, `Timestamp`, `getCountFromServer` | 있음 (12.19.0) | 추가 SDK 파일 없음 |

- 문서의 `metadata.hasPendingWrites`가 `true`인 변경(이 기기의 확정 전 쓰기)은 사본에 합치지 않는다. 서버가 확정하면 다시 도착하므로 그때 합친다.

### 3.4 데이터

**Firestore 문서** (경로·필드는 D-020 그대로, 묘비만 추가)

```js
// 북마크 (지금과 같음)
{ title, url, category, addedAt, order, updatedAt }
// 묘비 (새로 추가): 삭제한 북마크. 다른 필드는 지운다
{ deleted: true, updatedAt: <serverTimestamp> }
```

- 기존 문서는 이전할 필요가 없다. 모두 `updatedAt`이 있고, `deleted`가 없으면 북마크로 본다.
- v0.5 앱은 `orderBy('order')`로 구독하므로 `order`가 없는 묘비는 보이지 않는다 → 새 앱이 만든 묘비는 v0.5 앱에서 **삭제된 것으로 보인다** (호환됨).

**`localStorage` 사본** `single_file_bookmarks_cloud_copy_<uid>`

```js
{
  version: 1,
  lastSync: 1790662241437,   // 받은 문서의 updatedAt 중 가장 큰 값(ms, 서버 시각)
  lastFullSync: 1790662241437, // 마지막으로 전체를 받은 시각(기기 시각, 3.6의 주기 판단용)
  items: [ { id, title, url, category, addedAt, order } ]  // 묘비는 넣지 않음
}
```

- 사본도 외부 입력이다: 불러올 때 `try`로 감싸 파싱하고, 항목마다 `normalizeBookmark` + `order` 숫자 검사. 깨졌거나 `version`이 다르면 버리고 전체를 다시 받는다.
- `lastSync`는 **기기 시계가 아니라 서버의 `updatedAt`**에서 가져온다(기기 시계가 틀려도 빠뜨리지 않음). 같은 시각의 문서를 놓치지 않도록 `>`가 아니라 `>=`로 조회하고, 다시 온 문서는 같은 내용으로 덮어쓴다(멱등).
- 저장 실패(용량 초과)는 알림 없이 넘기고 다음에 열 때 전체를 받는다. 500개 기준 약 150KB로, 한도(약 5MB)의 3%.

### 3.5 동작

| 시점 | 동작 |
|---|---|
| 앱 열기 (로그인한 채 닫았음) | 사본이 있으면 **바로 보여 준다**(K-16의 "불러오는 중…" 대신). 계정 준비 전까지는 추가·복구·가져오기 버튼과 카드의 수정·삭제·이동을 막는다(보기·검색·내보내기는 가능) |
| 로그인 확인 후 | `where('updatedAt', '>=', Timestamp.fromMillis(lastSync))` 구독 시작. 받은 변경을 사본과 화면에 합침 |
| 받은 문서 | `deleted: true` → 사본에서 제거. 그 밖 → `normalizeBookmark`로 검증해 추가·교체(`order` 포함). `hasPendingWrites` 문서와 `removed` 변경은 무시. 합친 뒤 `order`로 정렬하고, 목록이 달라졌을 때만 다시 그림(지금과 같음) |
| 추가·수정·이동 | 지금과 같음(`setDoc`/`updateDoc`). 사본도 즉시 고침 |
| 삭제 | `deleteDoc` 대신 **묘비로 `setDoc`**. 덮어쓰기 복구의 "새 목록에 없는 문서"도 묘비로 |
| 쓰기 거부 | 지금의 `trackUpdate`처럼 서버에서 그 문서를 다시 읽어 **사본을 서버 값으로 맞춘다**(없거나 묘비면 제거, 있으면 교체). 수정·이동이 묘비 때문에 거부된 경우는 "삭제가 이김"으로 알리지 않음(묘비도 "없음"으로 판단하도록 조건을 바꿈) |
| 첫 로그인 이전 (D-019) | 사본이 없으니 전체를 받고(3.6의 전체 받기), 서버에서 받은 결과로 클라우드가 비었는지 판단해 지금처럼 묻는다 |
| 로그아웃 | 지금처럼 Firestore 캐시를 지우고, **사본도 지운다**(공용 기기 보호). 다음 로그인은 전체를 받음 |

- **"삭제가 이긴다"는 규칙(D-020)은 유지된다:** 묘비 문서에 다른 기기의 늦은 `updateDoc`(일부 필드)이 도착하면, 합친 결과에 `deleted`와 북마크 필드가 섞여 규칙에 걸려 거부된다.
- 전체 쓰기(`setDoc`, 복구 병합)는 묘비를 덮어써 북마크를 되살릴 수 있다. 복구는 사용자가 원한 것이므로 수용.

### 3.6 주기적 전체 동기화

바뀐 것만 받으면 다음을 놓칠 수 있다.
- 묘비가 아니라 **문서가 지워진 경우**: v0.5 앱이 삭제했거나 콘솔에서 직접 지운 경우
- 사본이 어떤 이유로 서버와 어긋난 경우

그래서 **마지막 전체 동기화로부터 7일이 지나면**(Q5) 앱을 열 때 전체를 다시 받고, 서버 결과에 없는 항목을 사본에서 뺀다. 이때 **확정 안 된 쓰기가 없을 때만** 한다(`waitForPendingWrites`가 끝난 뒤). 그렇지 않으면 방금 추가한 항목이 잠시 사라진다.

**전체 받기의 방법** (새 기기·로그인 직후·7일마다 공통)
- `getDocsFromServer(query(col, orderBy('order')))`로 한 번 받는다. **묘비는 `order`가 없어 결과에 들어오지 않는다** → 비용은 살아 있는 북마크 수뿐이고, 묘비가 쌓여도 늘지 않는다.
  - 묘비까지 읽으면 하루 10개 삭제 × 1년 = 묘비 3,650개일 때, 기기 3대의 주간 전체 동기화만으로 하루 약 1,600회가 더 읽힌다. 이를 피하기 위함.
- 결과로 사본을 **교체**하고, `lastSync` = 결과 문서들의 `updatedAt` 최댓값(결과가 비면 `0`), `lastFullSync` = 지금(기기 시각, 주기 판단에만 씀).
  - `lastSync`에 기기 시각을 쓰지 않는 이유: 기기 시계가 서버보다 빠르면 그 차이만큼의 변경을 다음 전체 동기화까지 놓친다. 서버 시각인 `updatedAt`만 쓴다.
  - 대가: 가장 최근에 바뀐 살아 있는 북마크보다 **뒤에 생긴 묘비**는 이어지는 구독에서 한 번 더 읽힌다(마지막 추가·수정 이후의 삭제 수만큼). 계정이 비어 있으면 묘비 전체를 한 번 읽는다. 둘 다 전체 동기화 때만이고 양이 작아 수용.
- 받는 동안 생긴 묘비·변경은 `updatedAt >= lastSync` 구독이 이어서 받으므로 놓치지 않는다.
- 오프라인이면 전체 받기를 미루고 사본으로 동작한다(사본이 없으면 SDK 캐시의 스냅샷 → 없으면 빈 목록 + "연결 중").

### 3.7 보안 규칙 변경

```
function isTombstone(d) {
  return d.keys().hasOnly(['deleted', 'updatedAt'])
    && d.keys().hasAll(['deleted', 'updatedAt'])
    && d.deleted == true
    && d.updatedAt == request.time;
}

match /users/{uid}/bookmarks/{bookmarkId} {
  allow read, delete: if isAllowedOwner(uid);
  allow create, update: if isAllowedOwner(uid)
    && (isValidBookmark(request.resource.data) || isTombstone(request.resource.data));
}
```

- `delete`는 남겨 둔다(묘비 정리, v0.5 앱 호환).
- `updatedAt` 단일 필드 조건 조회는 Firestore가 자동으로 만드는 색인으로 된다(색인 설정 불필요).
- **게시 순서:** 새 규칙은 v0.5 앱과도 호환된다. **앱을 배포하기 전에 규칙을 먼저 게시**한다. 거꾸로 하면 새 앱의 삭제가 거부된다.

북마크 500개, 기기 3대, 하루 20번 열기, 하루 변경 10건 기준.

| | 지금 (v0.5) | 바뀐 것만 받기 |
|---|---|---|
| 앱 열 때 | 최대 500 × 60 = 약 30,000 / 일 | (그사이 변경 ≈ 10 + 1) × 60 = 약 660 / 일 |
| 내 쓰기가 되돌아옴 | 0 | 쓰기 1건당 기기마다 1 (≈ 30 / 일) |
| 주기적 전체 동기화 | - | 500 × 3 / 7일 ≈ 215 / 일 (묘비는 읽지 않음) |
| **합계** | **약 30,000 / 일** (한도 50,000) | **약 1,000 / 일** |

### 3.10 묘비 비우기 (사용자가 실행)

자동 정리는 하지 않고(Q6), 로그인 중 사용자가 필요할 때 묘비 수를 보고 비울 수 있게 한다.

1. 동기화 상태 표시(`✓ 동기화됨` 등)를 누르면(Q7) `getCountFromServer(query(col, where('deleted', '==', true)))`로 묘비 수를 센다. **확인함(2026-09-29): 단일 조건이라 색인 설정 없이 동작**하고, 비용은 묘비 1,000개당 읽기 1회.
2. 확인 창: "삭제 기록 **N**개(약 **X**KB)가 있습니다. 8일이 지난 기록을 비울까요?\n(다른 기기에서 지운 북마크가 되살아나지 않도록 최근 8일 기록은 남깁니다.)" — 용량은 묘비 1개를 약 150바이트(색인 포함 추정)로 계산.
3. 확인 → `getDocsFromServer(query(col, where('deleted', '==', true)))`로 묘비를 읽고, **`updatedAt`이 8일보다 오래된 것만** 앱에서 골라 500개 단위 `writeBatch`로 `delete`. 끝나면 "N개를 비웠습니다."
   - 읽기·삭제가 각각 묘비 수만큼 든다(3,650개면 각 3,650회, 하루 한도의 7%·18%). 사용자가 실행할 때만이므로 수용.
   - 오프라인이면 실행하지 않고 "연결된 뒤에 다시 시도해 주세요."
   - 여러 기기에서 동시에 눌러도 이미 지운 문서를 지우는 것은 무해하다.

**8일인 이유 (전체 동기화 주기 7일 + 여유 1일):** 지난 7일 안에 앱을 연 기기는 그보다 오래된 묘비를 이미 받아 반영했다. 7일 넘게 열지 않은 기기는 다음에 열 때 전체 동기화(3.6)를 하므로 묘비 없이도 서버와 같아진다. 따라서 **어느 기기도 삭제를 놓치지 않는다.** 전체 동기화 주기를 바꾸면 이 기준도 함께 바꾼다(주기 + 1일).

- 묘비를 지운 뒤 오프라인이던 기기의 늦은 `updateDoc`은 문서가 없어 거부되고, 3.5의 거부 처리로 조용히 사본에서 빠진다(삭제가 이김 유지). 늦은 전체 쓰기(`setDoc`: 복구 병합, 가져오기)는 북마크를 되살릴 수 있다 — 묘비가 있을 때와 같음.
- 규칙 변경 없음(`delete`는 이미 허용).

### 3.11 테스트

- 읽기 수 확인(3.8): 다시 열었을 때 서버에서 온 스냅샷의 문서 수 = 그사이 바뀐 문서 수(+같은 시각 1~2개). Firebase 콘솔 **Firestore → 사용량**의 읽기 그래프로도 확인(몇 분 늦게 반영)
- 두 기기: 추가·수정·삭제·이동이 서로 반영(삭제는 묘비). 한쪽 오프라인에서 수정, 다른 쪽에서 삭제 → 삭제가 이김, 알림 없음
- 사본: 로그인 상태로 새로고침 → 사본이 즉시 보이고 버튼이 막혔다가 풀림. 서버를 멈춘 오프라인 열기. 사본을 깨뜨려 넣으면 전체를 다시 받음
- 전체 동기화: `lastFullSync`를 8일 전으로 바꾸고 열기 → 콘솔에서 직접 지운 문서가 사본에서 빠짐
- 로그아웃 → 사본·캐시 삭제. 다시 로그인 → 전체 받기, 첫 로그인 이전 질문은 기기당 한 번 그대로
- v0.5 앱과 섞여 쓰일 때: 새 앱의 삭제가 v0.5에서 사라져 보임
- 묘비 비우기: 테스트 묘비의 `updatedAt`을 9일 전·1일 전으로 만들 수 없으므로(규칙이 `request.time`만 허용), 구현 때 "N일" 기준을 잠시 0으로 바꾼 사본으로 동작을 확인하고, 실제 기준(8일)에서는 최근 묘비가 남는지 확인. 개수·용량 표시, 오프라인일 때 안내

### 7.1 진행 방식
- 단계마다 새 세션에서 시작해도 된다. 요청 예: "docs/IMPORT-DELTA-DESIGN.md 7장의 1단계를 진행해줘."
- 첫 커밋 뒤 초안 PR을 열고, 본문에 완료 조건 체크리스트를 둔다. 커밋 메시지는 단계 번호로 시작한다(예: `1단계: 브라우저 북마크 HTML 가져오기`).
- 구현 중 설계를 바꿔야 하면 같은 브랜치에서 이 문서를 고치고 이유를 커밋 메시지에 적는다.
- 클라우드 테스트는 사용자 계정의 실제 데이터에 쓰므로 이름으로 구별되는 테스트 항목만 만들고 지운다(CLAUDE.md).
- 폰 테스트는 README "폰 테스트"(Pages 브랜치 전환) → 끝나면 `main`으로 되돌림.

| # | 질문 | 선택지 | 추천 / 결정 |
|---|---|---|---|
| Q1 | 가져오기 버튼 | (가) 지금의 [📂 복구] 하나로 JSON 백업과 북마크 HTML을 모두 받고 이름을 **[📂 가져오기]**로 바꿈 (나) [📥 브라우저 북마크] 버튼을 따로 추가 | **(가)** 헤더 버튼이 이미 많아 360px에서 세 줄이 됨. 파일 내용으로 자동 판별 |
| Q2 | 중첩 폴더의 카테고리 | (가) 가장 안쪽 폴더 이름 (`JS`) (나) 경로를 이어 붙임 (`개발/JS`) | **(가)** 카테고리 필터가 짧고, 이 앱의 내보내기를 다시 가져오면 그대로 돌아옴. (나)는 카테고리 수가 많아지고 100자 제한에 걸리기 쉬움 |
| Q3 | 제목이 빈 북마크 | (가) 호스트 이름(`example.com`)을 제목으로 (나) 건너뜀 | **(가)** 브라우저에서는 빈 제목 북마크를 흔히 씀. 나중에 [수정]으로 바꾸면 됨 |
| Q4 | "같은 URL"의 기준 | (가) `new URL().href`가 같을 때 (나) 여기에 더해 경로 끝 `/`와 `http`/`https` 차이도 무시 | **(가)** 다른 페이지를 같은 것으로 보고 빠뜨리는 쪽이 더 나쁨. 중복이 조금 남는 쪽을 택함 |
| Q5 | 전체 동기화 주기 | 7일 / 1일 / 30일 | **7일** 주 1회 × 북마크 수는 한도의 1% 미만 |
| Q6 | 묘비 정리 | (가) 자동 정리는 하지 않음 (나) 90일 지난 묘비를 앱이 자동으로 지움 (다) (가) + 사용자가 묘비 수를 보고 8일 지난 것을 직접 비움 | **(다) 확정.** 직접 비우기는 단일 조건 조회라 색인이 필요 없고, 사용자가 한 기기에서 실행하므로 기기 간 조정도 필요 없으며, 8일 기준이라 삭제를 놓치는 기기가 없다(3.10). 자동 정리(나)를 하지 않는 이유: 묘비는 읽기를 거의 늘리지 않고(3.6, 3.9) 저장 공간도 몇 MB 수준. 정리하려면 ① `deleted == true` + `updatedAt <` 조회용 **복합 색인을 콘솔에서 만들어야** 하고 ② 서버 코드가 없어 어느 기기가 언제 지울지 조정해야 하며 ③ 90일 넘게 오프라인이던 기기가 삭제를 놓침(7일 전체 동기화가 바로잡긴 함). 묘비가 수만 개 규모가 되면 따로 결정 |
| Q7 | 묘비 비우기를 여는 곳 | (가) 헤더의 동기화 상태 표시(`✓ 동기화됨` 등)를 누르면 확인 창 (나) 헤더에 [🧹 정리] 버튼 추가 (다) 계정 이름(이메일)을 누르면 | **(가) 확정.** 가끔 쓰는 관리 기능이라 버튼을 늘리지 않음. 동기화와 관련된 자리이고, 마우스를 올리면 "눌러서 삭제 기록 관리" 안내(`title`). 키보드로도 누를 수 있게 `<button>`으로 바꿈 |
