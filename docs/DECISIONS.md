## 1. 개요

`jdrbmmanager`는 **빌드 없이 정적 파일 몇 개로 동작하는 북마크 관리자**입니다. `index.html`을 브라우저로 열면 로그인 없이 쓰는 로컬 모드(`localStorage`)로 동작하고, 웹 주소로 열어 Google 계정으로 로그인하면 Firestore로 여러 기기에서 동기화됩니다(D-017). 서비스 워커로 오프라인에서도 열리고 홈 화면에 설치할 수 있습니다.

| 항목 | 내용 |
|---|---|
| 구성 | `index.html` (CSS → HTML → JS 순서, 앱 본체) + `sw.js`(서비스 워커) + `manifest.webmanifest`·`icons/`(설치용) + `firestore.rules`(보안 규칙, 콘솔에 게시) (D-018) |
| 실행 | `https://jaydrobin.github.io/jdrbmmanager/` (GitHub Pages, `main` 자동 배포) 또는 브라우저로 `index.html` 열기(로컬 모드만) |
| 저장소 | 로컬 모드 `localStorage` (브라우저·출처별로 분리됨). 클라우드 모드 Firestore `users/{uid}/bookmarks` + 기기의 IndexedDB 캐시 (D-019) |
| 외부 요청 | 파비콘 이미지(Google S2). `http(s)`로 열었을 때 버전 고정한 Firebase SDK(`www.gstatic.com/firebasejs/`)와 그 SDK의 Auth·Firestore 통신 (D-017) |
| UI 언어 | 한국어 |

## 3. 데이터 모델과 저장소

### 북마크 항목

```js
{
  id: 1790662241437017,     // number. 새 항목은 Date.now() * 1000 + 난수 세 자리 (D-003)
  title: 'GitHub',          // string, 필수. 500자 이하 (넘으면 잘라냄)
  url: 'https://github.com',// string, 필수. http(s) 스킴으로 보정됨. 2048자 이하 (넘으면 항목을 버림)
  category: '개발',         // string, 빈 문자열 가능. 100자 이하 (넘으면 잘라냄)
  addedAt: 1727600000000    // number(ms) 또는 null(모름). v0.4에서 추가 (D-015)
}
```

- 전역 배열 `bookmarks`가 유일한 상태이며, **배열 순서 = 화면 순서**입니다. 상태는 작업 함수(`addBookmark`·`updateBookmark`·`removeBookmark`·`moveBookmark`·`replaceAll`·`mergeAll`)로만 바꾸고, 저장은 저장소 계층 `store`가 맡습니다. 로컬 모드는 `localStorage`에 배열 전체를 쓰는 LocalStore, 클라우드 모드는 바뀐 문서만 쓰는 CloudStore입니다.
- 추가 시각만 저장하고 수정 시각은 저장하지 않습니다. JSON 백업 형식은 메모리 항목 배열 그대로이며, 로컬·클라우드 모드 어느 쪽에서 만든 백업도 다른 쪽에서 복구할 수 있습니다.

### Firestore 문서 (클라우드 모드)

경로 `users/{uid}/bookmarks/{문서 ID}`, 문서 ID = `String(id)`. 메모리 항목에 `order`·`updatedAt`을 더한 형태이며, 두 필드는 CloudStore 안에서만 다룹니다 (D-020).

```js
{
  title: 'GitHub',             // string, 1~500자
  url: 'https://github.com',   // string, http(s)만, 2048자 이하
  category: '개발',            // string, 100자 이하, 빈 문자열 가능
  addedAt: 1727600000000,      // 정수(ms) 또는 null
  order: 1024,                 // number, 작을수록 앞. 새 항목 = 최소 - 1024, 이동 = 이웃 중간값
  updatedAt: <serverTimestamp> // 서버 시각. 규칙이 request.time과 같은지 검사
}
```

- 보안 규칙(`firestore.rules`)이 허용 UID·필드 목록·타입·길이를 검사합니다 (D-021). 앱의 `normalizeBookmark`·`MAX_*_LENGTH`와 같은 조건입니다. 앱은 길이를 JS `length`(UTF-16 단위)로 세며, 게시한 규칙에서 한글 500자·이모지 250개(`length` 500)가 통과하고 501자는 거부됨을 확인했습니다.
- 스냅샷 문서는 `normalizeBookmark`로 검증하고, 문서 ID와 항목 ID가 맞지 않거나 `order`가 숫자가 아니면 건너뜁니다.

### localStorage 키

| 키 | 값 |
|---|---|
| `single_file_bookmarks_v3` | `bookmarks` 배열 JSON (v0.4~) |
| `single_file_bookmarks_v2` | v0.3 이하 형식. v3 키가 없을 때 한 번 읽어 v3로 옮기고, 지우지 않고 남겨 둠 |
| `single_file_bookmarks_theme` | `'light'` 또는 `'dark'`. 사용자가 직접 전환했을 때만 저장됨 |
| `single_file_bookmarks_migrated_<uid>` | 첫 로그인 이전을 물은 시각(ms). 기기·계정마다 한 번만 묻기 위함 |
| `single_file_bookmarks_cloud_uid` | 로그인 중인 uid. 로그인할 때 쓰고 로그아웃할 때 지움. 다음에 열 때 "불러오는 중"을 보일지 정함 (K-16) |
| `firestore_*` | Firestore SDK가 여러 탭 조율에 쓰는 키 (앱이 직접 쓰지 않음) |

- IndexedDB에는 Firebase Auth의 로그인 상태(`firebaseLocalStorageDb`)와 Firestore 캐시가 있습니다. Firestore 캐시는 로그아웃할 때 지웁니다 (D-019).
- 서비스 워커 캐시(Cache Storage)는 `jdrbm-<버전>` 이름 하나만 남깁니다 (D-022).

- 키가 없으면 시드 데이터 3개(Google, GitHub, YouTube)로 시작합니다. 모두 삭제하면 `[]`가 저장되므로 시드가 다시 나타나지 않습니다.
- 값이 손상돼 있으면 원래 문자열을 `<키>_broken`에 보관합니다 (D-014).

## 4. 결정 목록

각 항목 형식: **상태** · 맥락 · 결정 · 결과(장점 / 대가).

### D-001. 단일 HTML 파일, 외부 의존성 없음
- **상태:** 대체됨 → D-017, D-018 (2026-09-29). v0.5부터 Firebase SDK(외부 코드)·서비스 워커 등 정적 파일 몇 개. 로컬 모드는 여전히 `index.html` 하나로 동작.
- **맥락:** 설치·빌드 없이 어디서나 열 수 있는 개인용 도구.
- **결정:** CSS·JS를 모두 `index.html`에 인라인. 라이브러리·번들러·패키지 매니저를 쓰지 않음.
- **결과:** 파일 하나만 복사하면 배포 끝. 대신 모듈 분리·자동 테스트·린트가 없고, 파일이 커질수록 탐색이 어려워짐.

### D-002. localStorage에 저장
- **상태:** 추정
- **맥락:** 서버가 없으므로 브라우저 내장 저장소가 유일한 선택지.
- **결정:** 변경 시마다 배열 전체를 `localStorage`에 JSON으로 저장 (LocalStore, v0.4까지는 `syncAndRender`). 로그인하면 Firestore (D-019).
- **결과:** 단순하고 즉시 저장됨. 대신 기기·브라우저 간 동기화가 없고, 사이트 데이터 삭제 시 함께 사라짐 → JSON 백업 기능(D-010)으로 보완.

### D-003. ID는 `Date.now()` 숫자
- **상태:** 추정
- **결정:** 새 북마크 ID를 생성 시각(ms)으로 사용. v0.5부터는 두 기기가 오프라인에서 같은 ID를 만들지 않도록 `max(Date.now() * 1000 + 0~999 난수, 최대 ID + 1)` (`generateId`).
- **결과:** 별도 카운터 없이 사실상 고유. 2255년까지 안전한 정수 범위. 이전 ID(ms)와 섞여 있어도 되며 형식이 같아 저장 키를 올리지 않음. 가져온 데이터의 ID 검증은 D-014.

### D-004. 새 북마크는 목록 맨 앞에 추가
- **상태:** 추정 (코드 주석 "신규 북마크는 최상단에 추가")
- **결과:** 방금 추가한 항목을 바로 볼 수 있음. JSON 병합과 브라우저 북마크 가져오기(D-024)도 가져온 항목이 앞에 붙어 같은 규칙을 따름.

### D-005. 매번 전체 다시 그리기 (innerHTML 템플릿)
- **상태:** 추정
- **결정:** 상태가 바뀌면 그리드를 비우고 모든 카드를 템플릿 문자열로 다시 생성. 사용자 텍스트는 `escapeHtml`로 처리.
- **결과:** 상태와 화면이 항상 일치하고 코드가 짧음. 수천 개 규모에서는 느려질 수 있고, 템플릿에 값을 넣을 때마다 이스케이프를 빠뜨릴 위험이 있음 (실제로 `href`에서 누락, 5장).

### D-006. HTML5 네이티브 드래그 앤 드롭, 전체 배열 기준 재배치
- **상태:** 추정
- **결정:** 카드 전체를 `draggable`로 두고, 드롭 시 **필터와 무관하게 전체 배열**에서 대상 위치로 이동.
- **결과:** 라이브러리 없이 구현. 필터 중에도 동작함. 대신 터치 기기와 키보드로는 드래그할 수 없어 이동 버튼으로 보완했고(D-016), 카드 텍스트 선택이 막힘(`user-select: none`).

### D-007. CSS 변수 기반 테마, `data-theme` 속성
- **상태:** 추정
- **결정:** 색상을 `:root`(라이트)와 `[data-theme="dark"]`에 변수로 정의하고 `<html>`의 `data-theme`로 전환. 사용자가 토글 버튼으로 직접 고르기 전에는 테마를 저장하지 않고 `prefers-color-scheme`을 따르며, 앱이 열린 동안 OS 설정이 바뀌어도 따라감 (2026-09-29, K-08).
- **결과:** 테마 추가·수정이 변수만으로 가능. 한 번 직접 고르면 그 뒤로는 OS 설정을 따르지 않으며, 다시 OS를 따르게 하는 UI는 없음. v0.3 이하에서 이미 저장된 테마 값은 사용자가 고른 것과 구별할 수 없어 그대로 유지됨.

### D-008. 파비콘은 Google S2 서비스 사용
- **상태:** 추정
- **결정:** `https://www.google.com/s2/favicons?domain=…&sz=64`로 아이콘을 불러오고, 실패하면 이미지를 숨김.
- **결과:** 사이트별 파비콘 경로를 몰라도 됨. 대신 저장된 모든 도메인이 Google로 전송되고, 오프라인에서는 아이콘이 보이지 않음. "외부 의존성 없음"(D-001)의 유일한 예외.

### D-009. HTML 내보내기는 Netscape 북마크 형식
- **상태:** 추정 (README의 "browser-compatible HTML export")
- **결정:** 크롬·파이어폭스·엣지가 가져올 수 있는 `NETSCAPE-Bookmark-file-1` 형식으로 출력. 카테고리 → 1단계 폴더, 카테고리가 없으면 `기본 북마크` 폴더. v0.6부터 `<META NAME="generator" CONTENT="jdrbmmanager">`로 이 앱이 내보낸 파일임을 표시한다(브라우저는 무시, 가져오기가 씀, D-024).

### D-014. 외부 입력은 검증 후에만 상태에 넣는다
- **상태:** 확정
- **날짜:** 2026-09-29
- **맥락:** 복구한 JSON과 `localStorage` 값을 그대로 쓰면서 스크립트 주입(K-01~K-03)과 앱 정지(K-04)가 가능했음.
- **결정:**
  - `localStorage` 불러오기, JSON 복구, 브라우저 북마크 가져오기(D-024), 모달 저장 네 경로 모두 `sanitizeBookmarks`/`isSafeUrl`로 검증한다.
  - 유효한 항목 = 제목이 비어 있지 않은 문자열이고 URL이 `http:`/`https:`. 아닌 항목은 **버린다**(복구 시 건너뛴 개수를 알림).
  - ID는 양의 정수로 정규화하고(`"7"` → `7`), 잘못되거나 없거나 **이미 쓰인** ID(병합 시 기존 목록, 또는 같은 목록의 앞선 항목)는 기존 최대값 이후로 새로 발급한다 (K-05). 새 ID는 `generateId`로 만든다 (D-003).
  - 제목 500자, 카테고리 100자, URL 2048자까지만 둔다 (Firestore 규칙과 맞춤, D-017). 넘는 제목·카테고리는 항목을 버리지 않고 잘라내고, URL은 자르면 다른 주소가 되므로 항목을 버린다.
  - Firestore 스냅샷의 문서도 같은 `normalizeBookmark`로 검증한다. 문서 ID와 맞지 않는 항목은 새 ID를 주지 않고 건너뛴다.
  - `localStorage` 값이 JSON이 아니거나 배열이 아니면 시드 데이터로 시작하되, 원래 문자열을 `single_file_bookmarks_v2_broken` 키에 보관한다.
  - 렌더링 시 `href`·`src` 속성값도 `escapeHtml`로 처리하고, 카드 버튼은 인라인 `onclick` 대신 클로저로 연결한다.
- **결과:** 외부 데이터로 스크립트를 실행하거나 앱을 멈출 수 없음. 대신 형식이 틀린 항목은 조용히 사라지고(불러오기 시), 스킴이 `http(s)`가 아닌 북마크(예: `ftp:`, `file:`)는 더 이상 저장할 수 없음.

### D-015. 추가 시각(`addedAt`) 저장, 저장 키 v3
- **상태:** 확정
- **날짜:** 2026-09-29
- **맥락:** 생성 시각을 저장하지 않아 HTML 내보내기의 `ADD_DATE`가 모두 내보낸 시각이었음(K-11). ID가 `Date.now()`이긴 하지만 D-014 이후로는 ID가 생성 시각이라는 보장이 없음.
- **결정:**
  - 항목에 `addedAt`(ms, 모르면 `null`) 필드를 추가한다. 새 북마크는 `Date.now()`, 수정은 기존 값 유지.
  - 저장 키를 `single_file_bookmarks_v3`로 올린다. v3 키가 없으면 `single_file_bookmarks_v2`를 읽어 v3로 옮기고, v2 키는 지우지 않는다.
  - `addedAt` 필드가 **없는** 항목(v2 저장값, v0.3 이하 JSON 백업)은 ID가 그럴듯한 시각(2000-01-01 이후 ~ 현재+1일)이면 ID를 추가 시각으로 추정하고, 아니면 `null`. 필드가 있는데 값이 잘못됐으면 `null`.
- **결과:** 내보낸 북마크가 브라우저에서 실제 추가 시각으로 보임. 이전 백업도 그대로 복구됨. 대신 추정값은 v0.3에서 복구 때 새로 발급된 ID면 복구한 시각이 되고, 시드 데이터는 추가 시각이 없음. v0.3 이하 앱에서 v3 데이터를 열면 v2 키의 옛 데이터가 보임(되돌리기용으로 남겨 둔 대가).

### D-017. Firebase로 여러 기기 동기화
- **상태:** 확정 (v0.5에서 구현. 세부 결정은 D-018~D-023)
- **날짜:** 2026-09-29
- **맥락:** PC 브라우저와 안드로이드 폰(크롬)에서 같은 목록을 써야 함. 조건은 Google 로그인, 오프라인에서도 열기·조회·추가·수정·삭제·순서 변경, Firebase **Spark(무료) 요금제** 안(결제 수단 등록 안 함). 하지 않는 것: 여러 사람의 목록 공유, 같은 북마크를 두 기기에서 고쳤을 때 내용 합치기, 아이폰 최적화, 로그인 없는 기기 간 동기화.
- **결정:** Firebase Auth(Google) + Firestore(오프라인 캐시)를 쓰고, 서비스 워커로 오프라인에서도 앱이 열리게 한다. 로그인하지 않으면 `localStorage`만 쓰는 로컬 모드. 호스팅은 GitHub Pages(`https://jaydrobin.github.io/jdrbmmanager/`, 공개 저장소, `main` 자동 배포)이고 Firebase Hosting은 쓰지 않는다.
  - 검토한 후보: Supabase(오프라인 동기화를 직접 구현해야 하고, 무료 프로젝트는 오래 안 쓰면 일시 정지), Google Drive 앱 데이터 폴더(파일 단위라 충돌·대기열을 직접 구현), 자체 서버(서버·인증 코드를 새로 써야 함), File System Access API(안드로이드 불가). **서버 코드 없이** 네 조건을 모두 만족하는 것은 Firebase뿐이었다.
- **결과:** 자동 동기화와 오프라인 사용. 대신:
  - 단일 파일·외부 의존성 없음(D-001)을 포기(D-018)하고 Firebase에 묶임. JSON 백업·HTML 내보내기를 유지하므로 언제든 데이터를 빼서 옮길 수 있음.
  - 저장 방식이 배열 전체 저장에서 문서(북마크) 단위 저장으로 바뀜 (D-020).
  - 무료 한도는 **읽기**가 가장 먼저 닿음: 앱을 열 때 리스너가 문서 수만큼 읽고, 30분 넘게 끊겼다 다시 연결되면 다시 전부 읽음. 북마크 500개·기기 3대·하루 20번 열기면 최대 약 10,000/일(한도 50,000/일). 쓰기·삭제 한도(각 20,000/일)는 전체 복구 1회에 500 정도. 한도를 넘으면 과금 없이 그날 요청이 거부되고, 앱은 캐시로 계속 보이며 쓰기는 대기 (K-18). 한도는 2026-09-29 Firebase 가격 페이지 기준.
  - 확인한 환경은 PC 크롬과 안드로이드 크롬. 안드로이드 삼성 인터넷은 브라우저 설정을 바꿔야 로그인됨 (K-17). 아이폰은 확인하지 않음.

### D-018. 정적 파일 몇 개, 버전 고정 Firebase SDK를 동적 import
- **상태:** 확정
- **날짜:** 2026-09-29
- **맥락:** 오프라인에서 앱을 열려면 서비스 워커가 필요한데 서비스 워커는 별도 파일이어야 함. Firebase SDK도 외부 코드. 그래도 빌드 없이 파일만 올리면 되는 구성은 유지하고 싶음.
- **결정:**
  - 파일: `index.html`(앱 본체, 지금처럼 한 파일), `sw.js`(D-022), `manifest.webmanifest`·`icons/`(설치), `firestore.rules`(D-021). 빌드 도구·패키지 매니저는 쓰지 않는다. 호스팅 전용 설정 파일(`firebase.json` 등)은 두지 않는다 (D-023).
  - Firebase SDK는 공식 CDN `https://www.gstatic.com/firebasejs/12.19.0/`의 `firebase-app.js`·`firebase-auth.js`·`firebase-firestore.js`를 **버전 고정**해 쓴다. 버전은 `index.html`의 `FIREBASE_SDK_URL`과 `sw.js`의 `SDK_BASE` 두 곳에 있다.
  - 스크립트를 `<script type="module">`로 바꾸지 **않고**, 일반 스크립트에서 동적 `import()`로 SDK를 불러온다. 모듈 스크립트는 함수가 전역이 아니라 인라인 `onclick`(D-012)이 깨지고, 정적 `import`는 SDK를 못 받으면 스크립트 전체가 멈추기 때문. 불러오지 못하거나 10초가 넘으면 로컬 모드로 동작한다.
  - 외부 요청 허용 목록: 파비콘(D-008), `www.gstatic.com/firebasejs/`, Firebase SDK가 스스로 하는 Auth·Firestore 통신. 이 밖의 요청은 추가하지 않는다.
- **결과:** 여전히 빌드 없이 파일을 올리면 배포 끝. 대신 SDK 버전을 올릴 때 두 파일을 함께 고쳐야 하고(CLAUDE.md), `file://`로 열면 로그인·오프라인 셸 없이 로컬 모드로만 동작.

### D-019. 로컬 모드와 클라우드 모드
- **상태:** 확정
- **날짜:** 2026-09-29
- **맥락:** 로그인하지 않거나 Firebase를 쓸 수 없어도 지금처럼 써야 하고, 로그인 전후의 데이터가 섞이면 안 됨.
- **결정:**
  - 로컬 모드: 로그인 안 함, `file://`, SDK 로드 실패. 원본은 `localStorage`(`single_file_bookmarks_v3`), 동기화 없음. 클라우드 모드: 로그인함. 원본은 Firestore, 기기에는 SDK의 IndexedDB 캐시.
  - 두 모드는 목록을 따로 쓴다. 로그인 중에는 로컬 목록을 건드리지 않고, **로그아웃하면 로그인 전 로컬 목록**으로 돌아간다. 로그아웃할 때 클라우드 캐시를 지우고(`terminate` → `clearIndexedDbPersistence`), 아직 올라가지 않은 쓰기가 있으면(`waitForPendingWrites`가 3초 안에 안 끝남) 먼저 묻는다. Firestore 인스턴스는 로그인할 때 만들고 로그아웃할 때 없앤다.
  - **첫 로그인 이전:** 기기·계정마다 한 번(`single_file_bookmarks_migrated_<uid>`), 서버에서 받은 첫 스냅샷 뒤에 묻는다. 로컬에 사용자 데이터가 있으면 클라우드가 비었을 때 "계정에 올릴까요?", 있을 때 "계정 목록에 합칠까요?" → 확인하면 `mergeAll`(ID 충돌은 D-014대로 새로 발급). 로컬이 비었거나 시드만(ID 1·2·3, 제목·URL 같음) 있으면 묻지 않는다. 로컬 데이터는 지우지 않는다. 여러 탭이 함께 묻지 않도록 묻기 전에 키를 기록한다.
  - **불러오는 중 표시 (K-16):** 로그인 중인 uid를 `single_file_bookmarks_cloud_uid`에 두고, 다음에 열 때 있으면 첫 스냅샷까지 로컬 목록 대신 "계정 목록을 불러오는 중…"을 보이며 추가·가져오기·내보내기 버튼을 막는다. SDK 로드 실패나 로그인이 풀려 있으면 로컬 목록을 보인다. 로그인 직후 첫 스냅샷 전에도 같은 상태.
- **결과:** 로그인 없이도, Firebase가 없어도 앱이 동작하고, 계정 목록과 로컬 목록이 섞이지 않음. 대신 로그아웃하면 그 기기에서 계정 목록이 안 보이고(다시 로그인하면 받음), 첫 로그인 이전을 한 번 거절하면 다시 묻지 않음(JSON 백업·복구로 옮길 수 있음).

### D-020. 클라우드 저장은 문서 단위, 순서는 `order` 필드, 마지막 쓰기가 이김
- **상태:** 확정
- **날짜:** 2026-09-29
- **맥락:** 배열 전체를 저장하면 두 기기가 서로의 변경을 통째로 덮어씀.
- **결정:**
  - 상태 변경은 작업 함수(`addBookmark`·`updateBookmark`·`removeBookmark`·`moveBookmark`·`replaceAll`·`mergeAll`)로만 한다. 각 함수는 ① 메모리 배열을 바꾸고 ② 바로 다시 그린 뒤 ③ `store`에 저장을 맡긴다. `store`는 LocalStore(배열 전체를 `localStorage`에) 또는 CloudStore(바뀐 문서만 Firestore에).
  - CloudStore: 추가 `setDoc`, 수정 `updateDoc`, 삭제 `deleteDoc`, 이동은 옮긴 문서의 `order`만 `updateDoc`, 복구 덮어쓰기는 새 목록에 없는 문서 삭제 + 전부 쓰기, 병합은 쓰기(모두 500개 단위 `writeBatch`).
  - 순서: 새 항목은 `최소 order - 1024`, 이동은 앞뒤 이웃 `order`의 중간값(**이동 한 번 = 쓰기 한 번**), 이웃 간격이 `1e-6`보다 작아지면 전체를 1024 간격으로 다시 매긴다.
  - 새 ID는 `max(Date.now() * 1000 + 0~999 난수, 최대 ID + 1)` (D-003). 두 기기가 오프라인에서 같은 ID를 만들지 않도록.
  - Firestore 쓰기의 Promise는 기다리지 않는다(오프라인에서는 끝나지 않음). 오류는 `.catch`로 받아 알린다(5초에 한 번). 서버가 거부하면 SDK가 화면의 변경을 되돌린다.
  - 원격 변경은 `onSnapshot(orderBy('order'))`로 받아 `bookmarks`를 교체한다. 스냅샷 문서도 외부 입력으로 검증한다(D-014). 만든 목록이 지금 목록과 같으면 다시 그리지 않는다(내 기기의 쓰기는 이미 그렸고, 다시 그리면 이동 버튼의 포커스가 사라짐).
  - **충돌:** 문서 단위로 마지막에 서버에 도착한 쓰기가 이긴다. 서로 다른 북마크의 변경은 모두 반영된다. 한쪽이 지운 북마크를 다른 쪽이 고치면 삭제가 이긴다: 일부 필드만 보내는 `updateDoc`은 없는 문서에서 규칙 검사의 `permission-denied`로 실패하므로, 수정·이동이 거부되면 서버에서 문서를 다시 읽어 없으면 알리지 않는다.
- **결과:** 기기 간에 서로의 변경을 덮어쓰지 않고, 이동이 싸다. 대신 같은 북마크를 두 기기에서 고치면 한쪽 내용이 사라지고, 덮어쓰기 복구 중 다른 기기의 늦은 오프라인 쓰기로 항목이 되살아날 수 있음 (K-19).

### D-021. Google 팝업 로그인, 허용한 UID만 데이터 접근
- **상태:** 확정
- **날짜:** 2026-09-29
- **맥락:** 누구나 Google 로그인 자체는 할 수 있음. 앱 주소(`github.io`)와 Firebase `authDomain`(`firebaseapp.com`)이 다름.
- **결정:**
  - 어느 호스팅에서든 `signInWithPopup`이 기본. 요즘 브라우저는 다른 사이트의 저장소 접근을 막아, 앱 주소와 `authDomain`이 다르면 리디렉트 로그인이 실패할 수 있다(Firebase 문서). 그래서 리디렉트는 앱 주소가 `authDomain`과 같을 때만(= Firebase Hosting의 `firebaseapp.com`으로 옮겼을 때) 팝업이 막혔을 때의 대체로 쓴다. 그 밖에 팝업이 막히면 "팝업을 허용해 주세요" 알림.
  - 앱 주소는 Firebase 콘솔의 승인된 도메인에 있어야 한다(`jaydrobin.github.io`, `localhost`).
  - Firestore 보안 규칙(`firestore.rules`)에서 **허용 목록의 UID만** 자기 경로(`users/{uid}/bookmarks`)를 읽고 쓰게 한다. 쓰기는 필드 목록·타입·길이(제목 500, URL 2048·`http(s)`, 카테고리 100)·`updatedAt == request.time`을 검사한다. 앱의 검증(D-014)과 같은 조건을 유지한다. 규칙은 저장소에 두고 콘솔에 붙여넣어 게시한다.
  - Firebase 설정값(`apiKey` 등)과 허용 UID는 공개돼도 되는 값이라 `index.html`의 `FIREBASE_CONFIG`와 `firestore.rules`에 그대로 둔다. 비밀 값(서비스 계정 키 등)은 저장소에 넣지 않는다.
  - 허용 계정은 1개. 계정마다 목록이 따로이므로 모든 기기에서 같은 계정으로 로그인한다. UID를 규칙에 추가하면 다른 계정도 자기 목록을 쓸 수 있다(무료 한도는 함께 씀).
- **결과:** 다른 계정은 로그인해도 "접근할 수 없습니다" 알림 후 로그아웃되고, 남이 무료 한도를 쓰지 못함. 로그인 상태는 Auth SDK가 IndexedDB에 두므로 오프라인에서도 로그인된 채 캐시를 씀. 대신 팝업이나 로그인 중의 주소를 가로채는 환경에서는 브라우저 설정을 바꿔야 로그인되고(K-17), 허용 계정을 늘리려면 규칙을 다시 게시해야 함. 팝업 로그인 중 콘솔에 `Cross-Origin-Opener-Policy` 경고가 찍히지만 로그인에는 영향이 없음.

### D-022. 서비스 워커로 오프라인 앱 셸, 홈 화면 설치, 동기화 상태 표시
- **상태:** 확정
- **날짜:** 2026-09-29
- **맥락:** 네트워크 없이도 앱을 열어야 하고(Firestore는 데이터만 오프라인 처리), 폰에서 앱처럼 쓰고 싶음.
- **결정:**
  - `sw.js`를 `./sw.js`로 등록해 **앱 폴더 범위**만 다룬다. `https`와 `localhost`에서만 동작.
  - 설치 때 앱 셸(`./`, `./index.html`, 매니페스트, 아이콘)과 SDK 세 파일을 캐시(`CACHE_NAME`, 현재 `jdrbm-v0.6`). 릴리스마다 이름을 올리고, 이전 캐시는 `activate`에서 지운다.
  - 요청별 전략: 앱 본체·매니페스트는 **네트워크 우선**(새 버전을 바로 받기 위해. 4초 안에 응답이 없으면 캐시로 열고, 늦게 온 응답으로 캐시만 갱신), SDK·아이콘은 캐시 우선(버전이 URL에 있어 바뀌지 않음), Firestore·Auth 통신과 파비콘은 가로채지 않음(SDK가 오프라인을 직접 처리).
  - `manifest.webmanifest`: `start_url`·`scope`는 `./`, `display: standalone`, 아이콘 192·512(가운데 안전 영역에 그려 `any`·`maskable` 겸용).
  - 로그인 중 헤더에 동기화 상태: `✓ 동기화됨` / `… 연결 중`(온라인인데 스냅샷이 캐시에서 옴) / `⬆ 올릴 변경 있음`(`waitForPendingWrites`가 1초 넘게 안 끝남) / `⚠ 오프라인`(`navigator.onLine`이 false, 빨간색). "연결 중"은 앱을 열 때마다 잠깐 "오프라인"으로 보이지 않게 하려고 둔다.
- **결과:** 비행기 모드에서도 홈 화면 아이콘으로 열어 조회·수정할 수 있고, 연결되면 올라감(안드로이드 크롬에서 확인). 대신 오프라인 셸은 앱을 한 번 온라인으로 연 뒤부터 동작하고, 배포 직후 이전 캐시가 한 번 보일 수 있으며(다시 열면 새 버전), 릴리스 때 `CACHE_NAME`을 올려야 함.

### D-023. 호스팅 이식성과 같은 출처 공유
- **상태:** 확정
- **날짜:** 2026-09-29
- **맥락:** 처음에는 GitHub Pages지만 나중에 Firebase Hosting·Cloudflare Pages·Netlify·Vercel로 **앱 코드 수정 없이** 옮길 수 있어야 함. GitHub Pages는 `jaydrobin.github.io` 아래 모든 저장소의 페이지가 같은 출처라 저장 공간(`localStorage`, IndexedDB)을 함께 씀.
- **결정:**
  - 앱 안의 모든 경로는 상대 경로(`./sw.js`, `manifest.webmanifest`, `start_url: "./"`, 아이콘). GitHub Pages는 하위 경로(`/jdrbmmanager/`), 다른 호스팅은 루트에서 서비스되기 때문.
  - 호스팅 전용 기능(주소 다시 쓰기, 응답 헤더, 리디렉트 설정)에 의존하지 않는다. 로그인은 팝업 기본(D-021), 보안 규칙은 호스팅과 따로 관리.
  - 같은 출처의 다른 페이지에 신뢰할 수 없는 외부 스크립트(광고·분석 등)를 넣지 않는다. 저장소 키는 `single_file_bookmarks_` 접두어, 서비스 워커는 앱 폴더 범위라 충돌하지 않는다. 사용자 사이트 저장소(`jaydrobin.github.io`) 루트에는 서비스 워커를 두지 않는다(모든 하위 경로를 가로챌 수 있음).

### D-024. 브라우저 북마크 HTML 가져오기
- **상태:** 확정 (v0.6에서 구현. 크롬에서 실제로 내보낸 파일, 클라우드 모드의 서버·다른 기기 반영, 안드로이드 폰에서 확인)
- **날짜:** 2026-09-29
- **맥락:** 이 앱은 브라우저 형식으로 내보낼 수만 있고(D-009), 크롬·엣지·파이어폭스에서 내보낸 북마크는 불러올 수 없었음.
- **결정:**
  - 헤더 버튼을 늘리지 않는다(360px에서 세 줄이 됨): [📂 가져오기] 하나로 JSON 백업과 북마크 HTML을 모두 받는다. 내용이 `<!DOCTYPE NETSCAPE-Bookmark-file-1`로 시작하거나(대소문자 무시) 확장자가 `.html`/`.htm`이면 북마크 HTML, 아니면 JSON 백업으로 처리한다. 내용의 시작만 보는 이유는 JSON 백업의 제목에 이 문자열이 들어 있어도 JSON으로 읽기 위해서다. 20MB가 넘는 파일은 형식과 관계없이 읽기 전에 거절한다(폰 메모리 보호).
  - 브라우저 내장 `DOMParser`로 읽는다(외부 라이브러리 없음). 만든 문서는 화면에 붙지 않아 스크립트가 실행되지 않고 이미지(`ICON` 등)도 받지 않는다. 값은 `textContent`·`getAttribute`로만 꺼내고 `normalizeBookmark`로 검증한다(D-014). 파싱한 HTML을 화면에 넣지 않는다.
  - 폴더(`<DT>` 안의 `<H3>` + 바로 뒤의 `<DL>`) → 카테고리. 중첩 폴더는 **가장 안쪽 폴더 이름**을 쓴다(경로를 이어 붙이면 카테고리가 많아지고 100자 제한에 걸리기 쉬움). 브라우저가 만든 최상위 폴더는 빼는데, `PERSONAL_TOOLBAR_FOLDER`·`UNFILED_BOOKMARKS_FOLDER` 속성이 있거나 경로의 첫 폴더 이름이 `BROWSER_ROOT_FOLDERS`(`북마크바`, `기타 북마크`, `모바일 북마크`, `북마크 도구 모음`, `북마크 메뉴`와 영어 이름들)에 있는 폴더다. 단, 이 앱이 내보낸 파일(`generator` 표시, D-009)은 폴더가 모두 카테고리이므로 빼지 않는다 — 이름만으로는 사용자의 카테고리 `기타 북마크`와 크롬의 `기타 북마크`를 가릴 수 없어서다. 경고하거나 이름을 바꾸게 하는 대신 파일에 표시를 두어, 사용자가 카테고리 이름을 고를 때 제약이 없게 했다. 이 앱이 카테고리 없는 항목에 쓰는 `기본 북마크`(`EXPORT_DEFAULT_FOLDER`)는 어느 파일이든, 어느 위치든 뺀다. 남는 폴더가 없으면 카테고리 없음.
  - 제목은 링크 텍스트이고, 비었으면 주소의 호스트 이름(브라우저에서는 빈 제목 북마크를 흔히 씀). `ADD_DATE`(초) → `addedAt`(ms). ms·µs로 보이는 값은 자릿수로 맞추고, 그럴듯한 시각(D-015)이 아니면 `null`. 아이콘·`LAST_MODIFIED`·태그는 앱에 없는 정보라 버린다.
  - `http(s)`가 아니거나(`javascript:`, `chrome://`, `place:`, `file:` 등) 2048자를 넘는 주소는 건너뛴다. 모달과 달리 `https://`를 붙여 보정하지 않는다.
  - **병합만** 한다(덮어쓰기 없음). `new URL(url).href`가 같으면 같은 주소다: 호스트 대소문자, 기본 포트, 호스트만 있는 주소의 끝 `/`는 같게 보고, 경로 끝 `/`·`http`↔`https`·쿼리·해시가 다르면 다른 주소(다른 페이지를 빠뜨리는 것보다 중복이 조금 남는 쪽을 택함). 지금 목록에 있는 주소와 파일 안에서 앞에 나온 주소는 건너뛴다.
  - 가져올 개수와 건너뛸 개수(이미 있는 주소, 가져올 수 없는 항목)를 `confirm`으로 보인 뒤, 파일 순서대로 목록 맨 앞에 붙인다(D-004). ID는 `sanitizeBookmarks(items, bookmarks)`가 새로 발급하고, 저장은 `mergeAll`(로컬 모드 `localStorage`, 클라우드 모드 500개 단위 배치 쓰기)이라 새 작업 함수·store 메서드가 없다.
- **결과:** 브라우저 북마크를 옮겨 올 수 있고, 이 앱의 HTML 내보내기를 빈 목록에 다시 가져오면 제목·카테고리·추가 시각(초 단위)이 그대로 돌아온다. 같은 파일을 두 번 가져오면 두 번째는 모두 건너뛴다. 대신 중첩 폴더 구조는 한 단계 카테고리로 줄고, 다음 카테고리는 다시 가져오면 카테고리 없음이 된다: 이름이 `기본 북마크`인 카테고리(카테고리 없는 항목과 같은 폴더로 내보내져 구별할 수 없음), 그리고 v0.5 이하에서 내보냈거나 브라우저를 거친(표시가 없는) 파일에서 브라우저 최상위 폴더와 이름이 같은 카테고리(예: `기타 북마크`). 5,000개 파일에서 읽기·중복 검사는 0.1초 안팎이고, 가져온 뒤 전체를 다시 그리는 데(D-005) 몇 초가 걸린다.

### D-025. 클라우드 모드에서 바뀐 것만 받기
- **상태:** 확정 (2026-09-29, 구현은 [IMPORT-DELTA-DESIGN.md](IMPORT-DELTA-DESIGN.md) 7장 2단계). 설계 3장
- **맥락:** 앱을 열 때마다 컬렉션 전체가 읽기로 계산돼, 읽기 수가 북마크 수에 비례함(K-18).
- **결정:** 계정 목록 사본을 `localStorage`에 두고 `updatedAt >= 마지막으로 받은 서버 시각`만 구독한다. 삭제는 묘비(`deleted: true`)로 남기고, 7일마다 묘비를 뺀 전체를 다시 받아 어긋남을 바로잡는다. 묘비는 자동으로 지우지 않고, 사용자가 개수를 보고 8일 지난 것을 직접 비울 수 있게 한다. 보안 규칙에 묘비를 허용한다(앱보다 먼저 게시).
